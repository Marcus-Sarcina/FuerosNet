# Test vectors — DRAFT

**Status: spec-derived and verified by no implementation.** These vectors were
written from `wire-format.md` alone, which is exactly the condition
`wire-format.md` §13 warns about: *vectors written from the spec alone encode
the spec's own mistakes.* That is their purpose here. They exist to be
attacked — **a disagreement between a vector and the specification is a finding
against one of them**, and either answer is progress. Canonical status waits on
an independent implementation reproducing every computed value.

The documents in this folder are generated by `tools/generate.py`
(Python 3 + the `cryptography` package for Ed25519); re-running it reproduces
them byte-for-byte. This file and `negative-vectors.md` are authored by hand.

| File | Contents |

| `primitives.md` | Deterministic CBOR atoms, seqno, path, Locator, a complete end-to-end `SignedLocator` signature, genesis back-pointers |

## What every vector assumes

- **Identities are synthetic and deterministic** — derivation rules at the top
  of `keys.md`. The ML-DSA-65 public keys are *not* valid lattice keys; nothing
  in an encoding or hashing vector depends on key validity.
- **No ML-DSA-65 implementation was available**, so post-quantum signature
  values are absent. Every PQ slot carries its exact `Sig_structure` (the bytes
  to be signed) and the envelope bytes that include zero-filled PQ slots are
  marked STRUCTURAL. Signing is the deterministic ML-DSA variant
  (`wire-format.md` §2.2).
- Deterministic CBOR per RFC 8949 §4.2 as profiled by `wire-format.md` §1:
  shortest-form integers, definite lengths, map keys sorted by the bytewise
  order of their encoded form, protocol maps keyed by unsigned integers.

## Interpretations taken

Places where the specification under-determines the bytes and this draft had to
choose. **Each is a review target**: if the choice is wrong, the vector is
wrong; if the specification permits more than one reading, the specification
needs a sentence.

1. **`SignedLocator` payload.** `wire-format.md` §2.3 says the subject signs
   "canonical CBOR of fields 1–2". Read here as the deterministic CBOR of the
   **two-entry map** `{1: subject, 2: Locator}`. Other defensible readings: the
   concatenation of the two encoded values, or a two-element array. The spec
   should fix one.
2. **Genesis back-pointer input.** §3.1's `SHA-256(the signer's keyhash)` is
   computed over the **raw 32 keyhash bytes**, not over a CBOR `bstr` wrapping
   of them.
3. **Verifier-selection hash inputs.** All §5 constructions
   (`nonce-commit`, `verifier-seed`, `rank`) are **raw byte concatenations** —
   ASCII tag bytes, raw 32-byte hashes, the 8-byte big-endian ordinal — with no
   CBOR framing. §5.3's layout strongly implies this; §5.1 and §5.4 say
   nothing either way.
4. **`COSE_Sign` outer structure.** Encoded untagged as
   `[h'', {}, null, [entries]]` — empty protected header as the zero-length
   byte string per RFC 9052, empty unprotected map, detached payload as CBOR
   null.
5. **`kid` value.** Header label 4 carrying the raw 32-byte keyhash as a
   `bstr`.
6. **Envelope carriage of the body.** Field 3 holds the body map directly (not
   wrapped in a `bstr`), and the COSE payload used in `Sig_structure` is the
   deterministic encoding of that map.
7. **`Participant` encoding.** `{1: keyhash}` only — the disclosable
   retention and client-integrity values appear nowhere in the body map, since
   they travel in the disclosure set (`wire-format.md` §4.5).

## Findings against the specification, found while drafting

1. **§3.1's signer-order table had no row for series reissue** (type 7). The
   table's generative rule — *the order the type's schema introduces its
   required signers* — yields node-then-patron, which these vectors use; the
   row was added to the table the same day.

## Reviewing this draft

The intended review asks three questions of every vector: does the encoding
follow from the cited section with no unstated choice; where a choice was
unavoidable, is it listed under *Interpretations*; and is there a malformed
input a decoder would plausibly accept that `negative-vectors.md` misses?
Checking arithmetic (hashes, signatures) matters less than checking
derivations — the arithmetic is mechanical, the derivations are where a spec
mistake would be encoded.
